# 无线竞速：技术方案（草案）

写于 2026-11-09。老师要求下一步重点做多人竞速，并单独上一节 micro:bit 无线（radio）课。本文是技术方案，还没开始写代码。

## 一句话

不用服务器，micro:bit 的无线就是网络。每台电脑跑自己的游戏；同一个种子，生成的路完全一样。每块板子把"我骑到哪了"广播出去，再把收到的别人的位置转给自己的游戏。游戏把对手画成半透明的车。转发的代码由学生自己写，不写就没有多人。

```
游戏A ─USB→ pos:1234:-2 ─→ 板A ─无线→ p:AMY:1234:-2 ─→ 板B ─USB→ rx:p:AMY:1234:-2 ─→ 游戏B
```

## 谁和谁比：组号就是赛道

micro:bit 的无线是广播，没有地址，也没有"连接"。同一个组号（`radio.config(group=…)`，0～255）的板子互相都听得到，听不到别的组。所以"匹配"就是选组号。

**建议：老师按座位分组。** 25 台电脑分 5 场，每场 5 人。
- 每场一个组号：11、12、13、14、15。不用 0，因为 0 是默认值，忘了设组号的板子会误入。
- 在电脑上贴一张卡片，比如 "RACE 12"。学生在代码里写 `radio.config(group=12)`，或者用积木"加入第 [12] 场比赛"。
- 板子不够时两人一组：一人骑，一人改代码。
- 可以加一场决赛：每场的第一名改用组号 20，老师电脑投影。

**开局前先确认匹配上了。** 比赛模式的开局画面显示：

```
RACE 12 · 我听到的人：AMY ▮▮▮  BEN ▮▮  CHLOE ▮▮▮  DAN ▮
```

名单根据刚收到的无线消息实时更新，旁边显示信号强度。谁没出现，就是组号写错了、无线没开，或者名字和别人重了。课上当场就能查出来，这一步本身就是调试练习。

**为什么不做自动匹配。** 自动匹配需要选主机、分配房间，还要处理消息丢失和重发。没有确认、没有地址的广播无线上做这些很脆弱，Y9 学生也看不懂。组号就是 MakeCode 里"设置无线组"的那个概念，学生已经会了。

## 消息格式

### 无线（板子之间）

每条尽量短。默认最长 32 字节，`radio.send` 自己还要占 3 字节头。

| 消息 | 意思 | 谁发、多久发一次 |
|---|---|---|
| `p:AMY:1234:-2` | AMY 骑到 1234 米，在 -2 米的车道上 | 每块板，每秒 4 次 |
| `f:AMY:72.35` | AMY 到终点了，用时 72.35 秒 | 冲线以后每秒 2 次，持续 10 秒（代替 `p:`） |
| `go:4821:uwa:2000` | 比赛开始：种子 4821，从 UWA 出发，2000 米 | 发令的板子（老师的板子，或者组里任意一块），0.5 秒内连发 5 次 |

**每条消息都带完整状态，不带"变化量"。** 丢一条没关系，0.25 秒后下一条就纠正了。这是这一课最重要的设计原则之一。

### USB（游戏和板子之间）

新增的协议消息，旧程序不认识就跳过：

| 方向 | 消息 | 意思 |
|---|---|---|
| 游戏 → 板子 | `pos:1234:-2` | 我现在的距离和车道，比赛中每秒 4 次 |
| 游戏 → 板子 | `fin:72.35` | 我冲线了 |
| 板子 → 游戏 | `rx:<收到的无线消息>` | 板子原样转发，游戏自己解析里面的 `p:`、`f:`、`go:` |
| 板子 → 游戏 | `name:AMY` | 我叫什么，每秒一次，跟 `hi:` 一起发 |

### 学生要写的转发代码（MicroPython，V1 和 V2 都能用）

```python
import radio
radio.on()
radio.config(group=12, queue=10)   # 12 = 你的比赛；queue 默认只有 3 条
NAME = "AMY"
...
while True:
    ...                                         # 转向、按钮，和以前一样
    for msg in messages():
        if msg.startswith("pos:"):
            radio.send("p:" + NAME + ":" + msg[4:])   # 告诉大家我在哪
        elif msg.startswith("fin:"):
            radio.send("f:" + NAME + ":" + msg[4:])
    heard = radio.receive()
    while heard:                                # 每一轮都把收到的读空
        print("rx:" + heard)                    # 把听到的转给游戏
        heard = radio.receive()
```

## 游戏这边做什么

- **一样的路。** 种子、出发场景、距离都从 `go:` 来。
  - 赛道生成本来就按种子和距离走。还要把假拐弯（现在用的是 `TickCount`）、路人、警察的随机数也固定下来。
  - 比赛中不理 `do:` 事件，关掉警察和卡通模式。
- **开局画面**：倒数 3、2、1；比赛中途再收到 `go:` 一律不理，防止有人捣乱。
- **对手**：半透明的车加名字牌，放在收到的距离和车道上，不会和你相撞。
  - 位置每秒只来 4 次，游戏按对手的速度在两次之间往前推，画面就不会一跳一跳的（航位推算，dead reckoning，网络游戏都这么做）。
  - 超过 2 秒没消息，对手变灰，显示"信号丢失"；超过 10 秒就去掉。
- **赛程条**：屏幕顶部从起点到终点一条线，每人一个点，实时显示名次。
- **撞车不结束比赛**：罚停 3 秒，原地继续。
- **冲线**：发 `fin:` 给板子；按收到的 `f:` 排名，最后出领奖台。
- **可疑数据**：两条消息之间前进的距离超过最高速度能骑的距离，就把这个对手标成 "?"。拿这个讨论冒充（有人发 `p:AMY:99999`）。

## 时间同步和公平

- 每台电脑从自己收到 `go:` 的那一刻开始计时。
- 无线延迟约 1 毫秒，板子循环最多 50 毫秒，USB 和游戏的一帧加起来几十毫秒，所以各台电脑的起跑差不到 0.1 秒。
- 成绩各自计时，排名以 `f:` 里的时间为准。

## 全班一起发，会不会挤爆

所有组号都在同一个频率上（默认 channel 7）。组号只决定收不收，发出去的消息在空中都会占用信道，不同组之间也会互相碰撞。

- **正常情况**：25 块板，每块每秒 4 次，共每秒 100 条。每条在空中约 0.35 毫秒，信道约 3.5% 的时间在用，大约 7% 的消息会因为碰撞丢掉。因为每条都是完整状态，这点损失看不出来。
- **有人狂发**：每个循环都发，每秒 20 次。全班加起来每秒 500 条，大约 30% 丢失，对手开始一卡一卡。
  - 这正好是课上要讲的：为什么要限速，为什么要每轮把队列读空。
- **进阶**：每场比赛用不同的 `channel`（不同频率），各场之间就不会互相碰撞了。

## 板子不够、用模拟器的同学

- 无线需要真的板子，模拟器之间没法真的比赛。所以两人一组共用一块板。
- 没有板子的同学也能写同样的转发代码：外壳通过模拟器的 `radio_input` 给它喂几个"机器人对手"的 `p:` 消息。代码在模拟器里能跑，拿到板子就能直接比赛。

## 风险，先验证

1. **V1 内存**：V1 只有 16 KB 内存。起步代码、积木生成的代码，再加上 `import radio` 和 `queue=10`，可能 MemoryError。要先在真的 V1 上试。
2. **机房实测**：用 10 块以上的板子同时发，看实际丢包率。可以写一个测试程序，屏幕上显示每秒收到几条。
3. **`display.scroll` 会卡住循环好几秒**：这几秒里队列满了，消息全丢。比赛程序里用 `display.show`，不用 scroll。

## 课上可以讲的（每一条游戏里都看得见）

- 广播和组号：一个班同时开 5 场，每场一个组号。
- 协议设计：`p:名字:距离:车道`，用 `split(":")` 拆开；长度上限。
- 丢包：队列满了就丢，信道挤了也丢。对比"发完整状态"和"发变化量"。
- 信号强度：`radio.receive_full()` 返回 RSSI，可以在 LED 上画信号格。
- 信任：谁都能冒充别人，游戏怎么发现。
